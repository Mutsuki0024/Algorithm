# 模块 1：LLM 基础 · 面试题

> 对应大纲：`../Agent_学习大纲.md` 模块 1。⭐ 表示高频题。答案按一句话结论 → 分点展开组织。

## Q: 大模型是怎么生成文本的？⭐

**答：** 本质是**自回归地预测下一个 token**。

1. 输入文本先经 Tokenizer 切成 token id 序列；
2. 模型输出下一个 token 在整个词表上的概率分布；
3. 按采样策略（温度、top_p 等）选出一个 token，拼回输入；
4. 重复这一过程，直到生成结束符或达到 max_tokens。

**追问：这对 Agent 设计有什么影响？** 一是模型无状态，多轮对话靠程序每轮重发历史，所以要做上下文管理；二是模型只输出工具调用意图，执行要靠程序；三是生成有随机性、错误会累积，所以要做校验和容错。

---

## Q: Token 是什么？为什么同样的意思中文更费 token？

**答：** Token 是模型处理文本的最小单元，由 Tokenizer 切分得到，主流算法是 BPE。

- BPE 从字节出发，反复合并语料中最高频的相邻片段，所以高频片段会成为 1 个 token，低频的会被拆开；
- 分词器的训练语料以英文为主时，英文合并得更充分，中文合并较少，所以同样的意思中文往往需要更多 token；
- 工程影响：计费、上下文上限、生成延迟都按 token 计算。

**追问：为什么模型数不清 strawberry 里有几个 r？** 模型看到的是 token（比如 "straw" + "berry"），不是单个字符，所以字符级任务天然容易出错。

---

## Q: 多轮对话中，模型是怎么"记住"前面内容的？⭐

**答：** 模型本身**无状态，不会记住任何东西**，是应用程序在每一轮请求时把**完整的历史消息重新发给模型**。

问题：

- 历史越来越长，**token 成本和延迟**随之增长；
- 最终会**超出上下文窗口**；
- 即使没超出，也会出现**上下文腐化**，模型对中间信息利用变差。

解决：滑动窗口、摘要压缩、长期记忆外置 + 按需检索、Prompt Caching 降低重复前缀的成本。

---

## Q: Agent 调用工具的过程中，模型做了什么，程序做了什么？⭐

**答：** **模型只负责"决定调什么、传什么参数"，程序负责"真正执行"。**

1. 程序把工具定义（名称、描述、参数 Schema）和对话一起发给模型；
2. 模型判断需要调工具，**输出一段结构化的调用意图**（工具名 + 参数）；
3. 程序解析这段输出，校验参数，**真正执行工具**（调 API、查数据库等）；
4. 程序把执行结果作为 tool 消息回填到对话里，再次请求模型；
5. 模型基于结果继续推理，决定继续调用工具还是给出最终回答。

这个循环就是 **Agent Loop**。

---

## Q: 讲一下 Transformer 的 QKV 和自注意力。⭐

**答：** 自注意力让每个 token 根据相关性，从上下文中的其他 token 收集信息。

- 每个 token 的向量经过三个线性变换得到 Q、K、V：**Q 表示"我要找什么"，K 表示"我能被怎样匹配"，V 表示"我携带的内容"**；
- 公式：`softmax(QKᵀ / √d_k) · V`。用 Q 和所有 K 做点积得到相关度，softmax 归一化成权重，再对 V 加权求和；
- Decoder-only 模型还会加**因果掩码**，每个位置只能看到前面的 token。

---

## Q: 为什么注意力分数要除以 √d_k？⭐

**答：** 防止点积过大，导致 softmax 饱和、梯度消失。

- 假设 Q、K 的各维度是均值 0、方差 1 的独立变量，那么点积的方差约等于 d_k；
- d_k 很大时，点积数值很大，softmax 输出接近 one-hot，大部分位置的梯度接近 0，训练不稳定；
- 除以 √d_k 能把方差缩放回 1 左右。

---

## Q: 多头注意力有什么用？

**答：** 让模型**同时从多个子空间关注不同类型的关系**。

- 把隐藏维度拆成 h 个头，各自独立计算注意力，最后拼接再做一次线性变换；
- 不同的头可以分别学到语法依赖、指代关系、位置邻近等不同模式；
- 每个头的维度变小，所以总计算量和单头基本相当。

---

## Q: 为什么长上下文很贵？

**答：** 注意力的计算复杂度是 **O(n²)**，而且 KV Cache 的显存占用随长度**线性增长**。

- 每个 token 都要和所有 token 计算注意力；
- 推理时要缓存所有历史 token 的 K、V，长度越长、并发越高，显存压力越大；
- 再加上上下文腐化，长上下文不仅贵，效果还不一定好。

---

## Q: 什么是 KV Cache？⭐

**答：** **缓存历史 token 的 Key 和 Value，避免每生成一个 token 都重复计算**，用显存换计算。

- 自回归生成时，第 t 步需要前面所有 token 的 K、V；如果不缓存，每步都要重新算整个序列；
- 有了 KV Cache，每步只需计算新 token 的 Q、K、V；
- 代价是显存占用随序列长度和并发数线性增长；
- 优化方向：GQA/MQA 减少 KV 头数、PagedAttention 分页管理、KV 量化。

**追问：Prompt Caching 是什么，和 Agent 有什么关系？** 跨请求复用相同前缀的 KV Cache。Agent 每轮都重发完整历史，前缀高度重复，命中缓存可以大幅降低成本和首 token 延迟。设计上要把稳定内容（system prompt、工具定义）放在前面，避免前缀里出现每次都变的内容。

---

## Q: 为什么输出越长越慢，而输入长的影响相对较小？

**答：** 推理分为 **Prefill** 和 **Decode** 两个阶段。

- Prefill 阶段一次性**并行**处理全部输入 token，GPU 利用率高；
- Decode 阶段每生成一个 token 都依赖上一个，只能**串行**，而且每步都要读取全部模型参数和 KV Cache，受显存带宽限制；
- 所以输入长度主要影响首 token 延迟，而输出长度直接决定总耗时。

**工程启示**：Agent 中要控制输出长度，比如让模型输出精简的结构化结果，而不是长篇解释；用户侧通过流式输出降低体感延迟。

---

## Q: 什么是上下文腐化（Context Rot）？⭐

**答：** **上下文越长，模型对其中信息的利用能力越差**，即使还远没有达到窗口上限。

- 典型现象是 Lost in the Middle，首尾信息利用得好，中间的信息容易被忽略；
- 无关信息越多，注意力越被稀释，推理质量下降；
- 结论：窗口能放下不等于模型能用好。要只放高信号的信息，做压缩、检索，用子 Agent 隔离上下文。

---

## Q: temperature 和 top_p 是什么？Agent 里怎么设置？

**答：** 两者都控制采样的随机性。

- **temperature**：用 `softmax(logits / T)` 调整分布的尖锐程度。T 小则更确定，T 大则更随机；
- **top_p**：只在累计概率达到 p 的最小候选集合里采样，候选数量随分布自适应；
- Agent 中的工具调用、结构化输出、分类抽取用**低温度**，保证稳定、可解析；创意类任务适当调高；
- 一般只调其中一个。

**追问：temperature 设为 0 就能保证输出完全一致吗？** 不能。GPU 浮点计算的非确定性、服务端的 batch 拼接等都会带来细微差异。稳定性要靠结构化输出约束、结果校验和重试来保证，不能依赖温度为 0。

---

## Q: 输出被截断会带来什么问题？

**答：** 达到 max_tokens 时输出会被直接截断，可能导致 **JSON 不完整、工具参数缺失**，进而解析失败。

处理方法：检查 stop_reason / finish_reason，如果是因长度截断，就提高上限、要求精简输出或续写；解析层要做校验和容错。

---

## Q: 大模型的训练流程是怎样的？

**答：** 一般分为 **预训练 → SFT → 偏好对齐 / 强化学习** 三个阶段。

- **预训练**：在海量文本上做下一个 token 预测，学到语言和世界知识，得到只会续写的基座模型；
- **SFT**：用（指令, 回答）数据微调，学会遵循指令、对话格式和工具调用格式；
- **对齐 / RL**：用 RLHF（奖励模型 + PPO）、DPO 或可验证奖励的 RL（RLVR），让模型更有用、更安全，并提升推理能力。

一句话：预训练给知识，SFT 教格式，RL 塑造行为和推理能力。

---

## Q: SFT 和 RLHF 有什么区别？哪个更适合快速迭代？

**答：** SFT 是**模仿学习**，学的是"标准答案长什么样"；RLHF 是**基于反馈优化**，学的是"哪个回答更好"。

- SFT 数据好构造、训练稳定、成本低，**适合快速迭代**，常用于格式、风格、特定任务能力；
- RLHF 能学到难以写出标准答案的偏好（有用性、安全性），上限更高，但流程复杂、训练不稳定；
- DPO 免去了奖励模型，是两者之间的折中。

**追问：基座模型越来越强，SFT 和 RL 的价值在哪？** 通用能力越来越依赖基座，SFT 的价值转向**垂直领域的行为定制和小模型蒸馏**；RL 的价值转向**可验证任务上的推理能力和 Agent 能力**，比如在真实工具环境中用任务成功率作为奖励来训练。

---

## Q: 推理模型和普通模型有什么区别？Agent 中怎么用？

**答：** 推理模型在回答前先生成较长的思维链，**用推理时的计算换取复杂任务的准确率**，能力主要来自可验证奖励的强化学习。

- 优点：规划、数学、代码、多步决策更强；
- 缺点：延迟高、token 成本高，简单任务性价比低；
- Agent 中：规划、复杂决策、Reviewer 等步骤用推理模型；路由、分类、抽取、摘要等用小模型，也就是**模型路由 / 大小模型搭配**。

---

## Q: 微调和 RAG 怎么选？⭐

**答：** **要补知识用 RAG，要改行为用微调。**

- RAG：适合私有、频繁更新、需要溯源的知识，更新只需改索引，成本低；
- 微调：适合固定输出格式、风格、领域话术、特定任务能力，或者把大模型能力蒸馏到小模型上以降低成本和延迟；
- 用微调来灌知识效果差：知识记不牢，更新成本高，还可能增加幻觉；
- 实践顺序：先 Prompt，不够再 RAG，还不够再微调，两者可以结合。

**追问：了解 LoRA 吗？** 冻结原模型参数，在权重旁加一对低秩矩阵 A、B（ΔW = BA），只训练这两个矩阵。可训练参数量通常不到 1%，显存需求低，可以为不同任务挂载不同的 LoRA 适配器。

---

## Q: 幻觉是怎么产生的？⭐

**答：** 根本原因是**模型的训练目标是"生成合理的续写"，而不是"生成真实的内容"**。

1. 训练目标：不知道时也会生成看起来合理的内容；
2. 知识缺陷：长尾知识学得不牢、数据有错、知识有截止日期；
3. 激励偏差：训练和评测奖励"答对"，不奖励"承认不知道"，模型倾向于自信地猜；
4. 解码随机性和滚雪球：一旦生成错误内容，后续会顺着错误继续编；
5. 上下文问题：上下文过长、检索结果冲突或不相关、Prompt 有歧义。

分类上可以分为**事实性幻觉**（违背事实）和**忠实性幻觉**（违背给定的上下文）。

---

## Q: 如何减轻幻觉？⭐

**答：** 幻觉无法根除，要**分层降低并兜底**。

- **输入层**：RAG 提供依据；Prompt 要求只依据资料回答，允许说"不知道"；
- **生成层**：低温度、结构化输出、要求标注引用来源；
- **工具层**：事实以工具返回为准；参数严格校验；
- **校验层**：规则校验、引用与原文比对、独立的 Reviewer 模型核查；
- **兜底层**：低置信度时拒答或转人工，高风险操作需人工确认。

**追问：用了 RAG 是不是就没有幻觉了？** 不是。检索不到、检索结果错误或冲突时，模型仍然会编造，或者不忠实于检索到的文档。所以 RAG 之后仍需要忠实度校验和引用核对。

---

## Q: Agent 场景下的幻觉有什么特殊之处？如何防止工具调用幻觉？⭐

**答：** Agent 的幻觉会**变成错误的动作，并沿着链路传播**，危害比聊天场景大。

常见形式：

- 调用不存在的工具，或编造参数（比如编造订单号）；
- 没有调用工具，却声称已经完成；
- 没有拿到结果，就自己编造工具返回值；
- 前面步骤的幻觉被后续步骤当作事实。

防范：

- 工具名用枚举约束，参数用 Schema 严格校验，ID 类参数做存在性检查，校验失败就把错误信息返回给模型让它修正；
- "是否完成"要以**程序侧的执行记录**为准，不能只听模型的说法；
- 关键步骤加中间结果校验或 Reviewer 节点；
- 高风险操作需要人工确认。

---

## Q: 幻觉率怎么衡量？

**答：** 把回答拆成**原子事实陈述**（claim），逐条判断是否被参考资料或标准答案支持，**不被支持的 claim 占比就是幻觉率**。

- 判定可以由人工标注，也可以用 LLM-as-Judge 加上人工抽检校准；
- RAG 场景常用**忠实度**（Faithfulness），即回答中的内容能否由检索到的上下文推出；
- 降幻觉的效果用**固定评测集上优化前后的幻觉率对比**来量化。
