# 模块 1：LLM 基础 · 学习笔记

> 对应大纲：`../Agent_学习大纲.md` 模块 1。

## 1.1 LLM 的本质与 Token

**一句话**：LLM 就是"根据前文预测下一个 token 的概率分布"，再加一个自回归循环。

```text
输入 → 模型 → 下一个 token 的概率分布 → 采样一个 token → 拼回输入 → 重复，直到结束符或长度上限
```

**三个对 Agent 至关重要的推论**：

| 特性 | 对 Agent 工程的影响 |
| --- | --- |
| 模型只会"续写文本" | 工具调用只是模型输出的一段结构化文本（调用意图），**真正执行的是程序**，也就是 Agent Loop |
| 模型无状态 | 多轮对话靠程序每轮**重新发送完整历史**，因此需要上下文管理和记忆设计 |
| 逐 token 生成，有随机性 | 输出不确定，错误会沿着链路传播，这是稳定性问题的根源 |

**Token 与 Tokenizer**

- Token 是模型处理的最小单元，模型实际看到的是 token id 序列。
- 主流分词算法是 **BPE**：从字节/字符出发，反复合并语料中最高频的相邻片段，直到词表达到预定大小。常见词合成 1 个 token，罕见词被拆成多个；因为能回退到字节，所以不存在未登录词（OOV）。
- 经验值：英文 1 token ≈ 4 字符 ≈ 0.75 词；中文 1 个汉字 ≈ 1～2 token（因分词器而异）。

Token 在工程上的影响：

- **计费**：按输入/输出 token 计费，输出更贵。
- **上下文上限**：窗口按 token 计算。
- **延迟**：输出逐 token 生成。
- **字符级任务易错**：数字母、反转字符串等，因为模型看到的是 token，不是字符。

**消息格式的本质**：system/user/assistant/tool 消息会被 Chat Template 拼成**一段带特殊标记的文本**，模型从 assistant 标记后开始续写。

> 推论：指令和数据在模型眼里都是同一串 token，没有硬隔离，这就是 **Prompt 注入**的根源。

## 1.2 Transformer 与注意力机制

**整体结构**：现在的 LLM 基本都是 **Decoder-only Transformer**。

```text
token ids → Embedding（+ 位置编码）→ N 层 [ 自注意力 → 前馈网络 FFN ]（每层带残差连接 + LayerNorm）→ 输出层 → 词表上的概率分布
```

- **自注意力**：让每个 token 从上下文里的其他 token 收集信息（"看谁"）。
- **FFN**：对每个位置单独做非线性变换（"想什么"），一般认为大量知识存储在 FFN 参数里。
- **因果掩码（Causal Mask）**：每个位置只能看到自己和前面的 token，不能看到后面的，这样训练和生成才一致。

**QKV 的直觉**：每个 token 的向量分别乘上三个矩阵，得到三种角色：

| | 含义 | 类比 |
| --- | --- | --- |
| **Q**（Query） | 我在找什么信息 | 搜索关键词 |
| **K**（Key） | 我能提供什么信息（用来被匹配） | 文档标题 |
| **V**（Value） | 我实际携带的内容 | 文档正文 |

**计算公式**：

```text
Attention(Q, K, V) = softmax( Q·Kᵀ / √d_k ) · V
```

1. `Q·Kᵀ`：当前 token 的 Q 和所有 token 的 K 做点积，得到相关度分数；
2. `/ √d_k`：缩放；
3. `softmax`：把分数变成权重（和为 1）；
4. `· V`：按权重对所有 V 加权求和，得到这个位置的新表示。

**为什么除以 √d_k**：Q、K 的维度 d_k 越大，点积的方差越大（方差约等于 d_k），数值会变得很大，softmax 就会极度尖锐，接近 one-hot，导致**梯度接近 0、训练不稳定**。除以 √d_k 可以把方差拉回到 1 左右。

**多头注意力（Multi-Head）**：把维度拆成 h 份，并行做 h 组独立的注意力，最后拼接。每个头可以关注不同类型的关系（语法、指代、位置……），相比单头表达能力更强，且总计算量基本不变。

**位置编码**：注意力本身不区分顺序，所以需要注入位置信息。现在主流用 **RoPE**（旋转位置编码），它天然编码相对位置，也便于扩展上下文长度。

**复杂度瓶颈**：每个 token 都要和所有 token 计算注意力，所以序列长度为 n 时，时间和空间复杂度都是 **O(n²)**。这是长上下文昂贵的根本原因。

## 1.3 上下文窗口、KV Cache、上下文腐化

**上下文窗口**：模型单次能处理的最大 token 数（**输入 + 输出**共享）。超出部分要么报错，要么被截断。

**推理的两个阶段**：

| 阶段 | 做什么 | 特点 |
| --- | --- | --- |
| **Prefill**（预填充） | 一次性处理整个输入 | 所有 token **并行计算**，偏计算密集；决定**首 token 延迟**（TTFT） |
| **Decode**（解码） | 逐个生成输出 token | 必须**串行**，每步依赖上一步；偏访存密集；决定生成速度（TPOT） |

> 这就是"**输出越长越慢，而输入长影响相对小**"的原因：输入可以并行处理，输出只能一个一个串行生成。

**KV Cache**：

- 问题：生成第 t 个 token 时，需要前面所有 token 的 K 和 V；如果每步都重新算，会有大量重复计算。
- 做法：把已经算过的 K、V **缓存起来**，每步只计算新 token 的 Q、K、V，再和缓存一起做注意力。
- 代价：**用显存换计算**。KV Cache 大小 ≈ `2 × 层数 × KV头数 × 头维度 × 序列长度 × 每元素字节数`，随序列长度线性增长，是长上下文和高并发场景的显存瓶颈。
- 优化：**MQA / GQA**（多个 Q 头共享 K、V 头，减少 KV 数量）、PagedAttention（vLLM，按页管理显存）、KV 量化等。

**和 Agent 工程的关系：Prompt Caching**

- 如果多次请求的**前缀完全相同**（system prompt、工具定义、历史消息），服务端可以复用这部分前缀的 KV Cache，**输入成本和首 token 延迟都会大幅下降**。
- 设计启示：**稳定的内容放前面，变化的内容放后面**；不要在 system prompt 里放时间戳这类每次都变的内容，否则会让缓存失效。
- Agent 每轮都会重发完整历史，所以前缀缓存命中率对成本影响很大。

**上下文腐化（Context Rot）**：

- 现象：上下文越长，模型对其中信息的利用能力越差，即使远没到窗口上限。
- 典型表现：**Lost in the Middle**，也就是开头和结尾的信息利用得好，中间的容易被忽略；无关信息越多，干扰越大，注意力被稀释。
- 结论：**"窗口能放下"不等于"模型能用好"**。上下文是稀缺资源，应该只放和当前任务最相关的高信号信息。这是上下文工程（模块 6）和子 Agent 上下文隔离（模块 7）的出发点。

## 1.4 采样参数

模型输出的是词表上每个 token 的打分（logits），**采样策略**决定最终选哪个 token。

| 参数 | 作用 |
| --- | --- |
| **Greedy**（贪心） | 永远选概率最高的，结果确定，但容易重复、死板 |
| **temperature** | `softmax(logits / T)`。T < 1 让分布更尖锐（更确定），T > 1 让分布更平（更随机），T → 0 近似贪心 |
| **top_k** | 只在概率最高的 k 个 token 里采样 |
| **top_p**（核采样） | 只在累计概率达到 p 的最小 token 集合里采样，候选数量随分布形状自适应 |
| **max_tokens** | 输出长度上限，超出就截断（要检查 stop_reason，否则会拿到不完整的 JSON） |
| **stop sequences** | 遇到指定字符串就停止生成 |

**选型经验**：

- 工具调用、结构化输出、分类、抽取：**低温度**（0～0.3），要的是稳定、可解析；
- 创意写作、头脑风暴：温度高一些；
- 通常只调 temperature 和 top_p 中的一个，不要同时大幅调整。

**易错点**：

- **temperature = 0 也不保证完全确定**：GPU 浮点运算的非确定性、batch 拼接等因素都会让输出有细微差异。所以**稳定性不能靠 temperature = 0 来保证**，要靠结构化输出约束、校验和重试（模块 9）。
- 部分推理模型对采样参数有限制或固定，以具体厂商文档为准。
- 输出被 max_tokens 截断是 Agent 里常见的 bug 来源，比如 JSON 不完整、工具参数缺失。

## 1.5 训练流程、推理模型、微调还是 RAG

**三阶段训练**：

| 阶段 | 数据 | 目标 | 产物 |
| --- | --- | --- | --- |
| **预训练** | 海量无标注文本（万亿级 token） | 预测下一个 token | 基座模型（Base）：有知识，但只会续写，不会"听指令" |
| **SFT**（监督微调） | 人工构造的（指令, 回答）对 | 学会对话格式、遵循指令，包括**工具调用格式** | 指令模型 |
| **偏好对齐 / 强化学习** | 偏好数据或可验证的奖励 | 让回答更有用、更安全、更符合人类偏好 | 对齐后的模型 |

**偏好对齐的几种方法**：

- **RLHF**：先训练奖励模型（Reward Model）给回答打分，再用 PPO 优化策略模型。效果好，但流程复杂、训练不稳定。
- **DPO**：不训练奖励模型，直接用（好回答, 坏回答）对优化，更简单稳定。
- **RLVR**（可验证奖励的强化学习）：在数学、代码等**结果可以自动判对错**的任务上，直接用正确与否作为奖励（如 GRPO 算法）。这是推理模型能力的主要来源。

> 一句话概括：**预训练给知识，SFT 教格式和指令遵循，RL 塑造行为和推理能力。**

**推理模型（Reasoning / Thinking Model）**：

- 在给出答案前先生成一段较长的思维链，通过 RL 训练出"拆解问题、尝试、自我检查、回溯"的能力；
- 本质是**用推理时的计算换质量**（Test-time Compute）：想得越多，复杂任务越准；
- 代价：延迟高、token 成本高，简单任务上性价比低；
- 和 Agent 的关系：推理模型适合规划、复杂决策等步骤；简单的分类、抽取、路由交给小模型，这就是**模型路由**的思路。新一代模型还支持在工具调用之间穿插思考（交错思考，Interleaved Thinking）。

**微调还是 RAG**：

| 需求 | 选择 | 原因 |
| --- | --- | --- |
| 注入**知识**（私有文档、频繁更新的数据） | **RAG** | 更新快、可溯源、成本低；微调记知识效果差，还容易引发幻觉 |
| 改变**行为**（输出格式、风格、领域话术、特定任务能力） | **微调** | 行为模式要靠训练才能稳定地内化 |
| 需要**低延迟 / 低成本**，把大模型能力迁移给小模型 | **微调 / 蒸馏** | 小模型 + 微调可以替代大模型 + 长 Prompt |

- 实际顺序：**先 Prompt → 不够再 RAG → 仍不够再微调**，两者也可以结合。
- 常用的高效微调方法：**LoRA**，冻结原参数，只训练低秩的增量矩阵，显存和存储成本都很低。

## 1.6 幻觉（Hallucination）

**定义**：模型生成的内容看起来流畅、合理，但**与事实不符，或与给定的上下文不一致**。

| 类型 | 说明 | 例子 |
| --- | --- | --- |
| **事实性幻觉** | 与真实世界的事实不符 | 编造论文、API、人物经历 |
| **忠实性幻觉** | 与输入或上下文不一致 | RAG 给了文档，回答却违背文档内容；摘要里加入原文没有的信息 |

**产生原因**：

1. **训练目标本身**：模型学的是"生成合理的续写"，而不是"说真话"。遇到不知道的内容，它也会生成看起来合理的内容；
2. **知识缺陷**：长尾知识学得不牢，训练数据有错，知识有截止日期；
3. **训练和评测的激励**：评测通常只看答对率，"猜一个"比"说不知道"得分更高，所以模型倾向于自信地猜；
4. **解码随机性**：采样可能选到低概率的错误 token，而且**一旦出错，后续会顺着错误继续编**（滚雪球效应）；
5. **上下文问题**：上下文过长导致信息被忽略、检索到的文档相互冲突或不相关、Prompt 有歧义。

**Agent 场景特有的幻觉**：

- **工具调用幻觉**：调用不存在的工具，编造参数值（比如编造一个订单号），或者**没调用工具却声称已经完成**；
- **伪造工具结果**：没拿到真实结果，就自己编了一个返回值继续推理；
- **链式传播**：前面步骤的幻觉被后续步骤当作事实使用，一路放大（模块 9 会详细讲）。

**缓解手段（分层）**：

| 层次 | 手段 |
| --- | --- |
| **输入层** | RAG 提供依据；Prompt 明确要求"只依据给定资料回答，不知道就说不知道"；减少无关上下文 |
| **生成层** | 低温度；结构化输出（Schema 约束）；要求附带**引用来源** |
| **工具层** | 用工具获取事实，**工具返回结果才是事实来源**；参数严格校验（枚举、格式、存在性检查） |
| **校验层** | 规则校验；引用和原文比对；Self-check 或独立的 Reviewer 模型核查；关键数据交叉验证 |
| **兜底层** | 置信度低时拒答或转人工；高风险操作需要人工确认 |

**如何衡量**：抽取回答中的事实性陈述（claim），逐条与参考资料或标准答案比对，计算不被支持的比例作为幻觉率；RAG 场景常用"忠实度"（Faithfulness）指标。具体方法在模块 11 展开。

**易错点**：幻觉**无法根除，只能降低和兜底**。面试时不要说"用 RAG 就能解决幻觉"，RAG 本身也会引入忠实性幻觉。
